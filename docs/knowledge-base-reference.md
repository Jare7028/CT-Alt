Research checked 4 October 2026 against public Connecteam Help Center articles. This is workflow evidence and an original CT Alt design proposal, not a claim of completed parity. No account interactions, fixtures, repository edits, hosted changes, notifications, uploads or paid services were used. Public reference HTML/text and two illustrations are cached only in `/tmp/ct-alt-knowledge-base-research/`; no competitor artwork should enter Git or CT Alt assets.

## Verified desktop workflow

1. **Create a base.** Add new → Knowledge Base → enter name → Save. The policy guide also describes Add New → Start from scratch → name. Multiple independently named bases are supported, with plan-dependent quantity. A department/topic can therefore have its own audience and management permissions.
2. **Build the hierarchy.** Add folder at bottom left creates a section folder. Select a section → + Add → Add folder creates a subfolder. A folder can contain text, links, files and further folders. The guides give deep nesting examples but no numerical nesting limit. The public illustration shows a left folder tree, central content and a right mobile preview; reproduce the workflow using CT Alt design, not this artwork.
3. **Create content.** Text → enter/paste → Save changes. Policy text supports bold, italic, underline, highlight, spacing, bullets/numbering and embedded links; the policy guide also mentions images/tables. Link → name and URL → Confirm. Files → select one or multiple local files → optionally rename → Save changes. Examples include PDFs, Word, images, video, CSV and Excel. CSV/Excel must be downloaded for viewing/editing; no spreadsheet editor is documented. Creating/uploading content is documented on web, not mobile.
4. **Organise.** Sibling folders/text/links/files can be reordered by their gray drag handle. An item's three-dot menu offers Move to a new folder and destination selection. Separate base order is changed through Mobile Preview drag/drop; dashboard column sorting is temporary. The guides do not establish whether a move can cross base boundaries.
5. **Assign the base.** Open base → Options → Edit Assignments → Smart Groups **or** Selected Users → choose audience → publish settings → review summary → Confirm. Assignment applies to **all** folders in that base. Individual-folder assignment is explicitly unsupported. Static users do not automatically include newly added employees. General Smart Group assignment is dynamic for current/future matching users. The Knowledge Base paragraph does not document an Updates-style fixed-vs-dynamic group toggle.
6. **Current user access.** User desktop sidebar → Knowledge Base → choose among bases they have access to → navigate folders/documents. “Without restrictions” in the user guide describes access to their assigned resources, not universal tenant access or permission to edit. Base audience and management permissions must remain separate.
7. **Find content.** Open the relevant base, search by file name/keyword, choose a result. File-name search is explicitly verified. Search across file bodies, OCR, attachments, all bases, or arbitrary rich-text content is not established by these guides.
8. **Inspect usage.** Overall Statistics reports base use. Folders and individual files also have insights: percent/count of assigned users who viewed at least once, a views trend for the last month, and assigned-user rows with view count and last viewed time. User search, extra columns, filters by Smart Groups/last viewed/total views/user details, selection actions, and Excel export are documented. Actions include tagging, notifying, individual Chat messages, team Chat creation and tasks. These actions are reference features, not permission to send anything during research.
9. **Confirm reading a policy.** The policy article recommends a separately assigned Quick Task with a shortcut to the policy and explicit task completion. Viewed metrics are not a policy acknowledgement, proof of reading, or a compliance signature.

## Management permissions and lifecycle boundaries

The permissions guide distinguishes **View** (dashboard summaries/objects, user filters, alerts), **Edit & Update** (edit/add/delete objects and assignments), and **Add New Knowledge Base** (create bases in addition to previous permissions). Administrators can be configured in the Users Admin section or via the feature/base permissions bubble. Toggles govern automatic inclusion of new administrators and whether administrators can add other administrators. The guide says permissions can be scoped within specific Knowledge Base categories/base instances. It does not precisely define whether an admin's management access also makes that admin an assigned reader or how those views enter the denominator.

Verified published-state evidence is limited: assignment has publish settings; the Insights illustration displays a Published badge; the Smart Group assignment article lists only published assets and sends draft/archived management back to the feature. Exact Knowledge Base draft editing, publish scheduling, unpublishing, archive/restore, deletion cascades and revision semantics are not documented in the read guides. Do not present invented lifecycle details as reference facts. Archive/restore can be an explicit CT Alt retention extension if chosen.

## Original CT Alt implementation proposal

### Desktop delivery that can be reviewed end to end

Keep the existing CT Alt shell/palette. Provide a base catalog, selected base's folder tree/breadcrumbs and a content list/reader. Multiple bases, top-level sections and nested folders should be real database objects. Offer keyboard-accessible Move and Move earlier/later controls alongside any drag/drop. Preserve ordered siblings and base order; distinguish persistent order from temporary name sort. Every company-preserving deep link must recheck permission.

Use tenant-bound bases, nodes and base-level assignments. A node has immutable identity, parent/base identity, type, title, position and revision; text/link/file metadata is type-specific. Reject cycles, cross-tenant destinations, invalid parents and unsupported cross-base moves. Explicit descendant handling is required before deleting/archiving a nonempty folder. A safe initial implementation can block nonempty-folder archive and document that retention choice rather than silently hide an entire subtree. Moving within a base must preserve content and view history by node ID. Cross-base moves need an explicit audience-change review and remain a separate increment if unsupported.

Start with current confirmed nonanonymous active-company owner/admin management and fixed selected **Auth user IDs** as the base audience, using an explicit documented capability model. Manager/employee reading must be assignment-based. This is a baseline CT Alt scope, not reference granular administrator parity. Do not assign a whole tenant by default or infer an audience from a missing/invalid assignment. Per-base/granular management must be a separate planned increment with tests before declaring parity. If a first release lacks files, rich text, nested folders, ordering or insights, list each omission in FEATURE_COVERAGE; do not label an unimplemented control complete.

Text should either use an audited structured document format with an allowlisted renderer or clearly labelled plain text. No arbitrary stored HTML execution. Named external links must reject javascript/data and other unsafe schemes; render external destinations intentionally. Images/tables, formatting, attachments and shortcuts require real implemented storage/rendering contracts, not simulated buttons.

### Private files within authorised free resources

File upload/download is a distinct verified backend capability. Root must choose and verify the existing CT Alt free-resource storage path and explicit quota before implementing it. No paid provisioning is proposed. Private object paths should bind tenant/base/node and immutable file version; authenticated storage policies and API reads must enforce the **same current base audience/management rules**, including company/member/Auth revocation. Do not use public buckets or expose a reusable cross-company object token.

Handle byte/type limits, quota accounting, filename safety, duplicate uploads and unknown upload outcomes explicitly. Prefer a signed-user upload path suitable for the chosen provider over sending a 200 MB body through an application route; 200 MB is the reference's advertised maximum, not an automatic CT Alt promise. An initial smaller supported file limit must be displayed and recorded. Downloadable bytes already received cannot be recalled. Short-lived signed URLs carry a bounded period of residual access; if immediate revocation is a product claim, design authenticated retrieval that checks current storage policy instead of assuming a previously issued URL is instantly revoked. Range requests/media previews, file deletion/version retention and malware handling need explicit decisions and tests.

### Reads, writes and recovery

Use coherent STABLE signed reads for catalog/tree/search/assignment/insights. Return exact identity/scope, bounded pages and appropriate definition/audience/content versions. Fresh signed access checks after a snapshot must reject current company/actor/role/base/audience changes before releasing private text, filenames, assignments or insight rows. Cursors bind company/actor/base/path/search/order and relevant versions; a removed parent or changed audience must produce a real error, not a successful empty result.

Mutations need current authority before payload-bound actor/company UUID receipts, revisions and short ordered locks around lifecycle/tree/order/assignment changes. Hold all manual/leaf reads during pending writes; use only exact in-memory retries and minimal field-free recovery markers. Failed recovery reads remain locked. Abort/generation-fence late tree/search/download/assignment/insight responses on path/base/company/filter changes, access denial or departure. Unknown write recovery reads all relevant lifecycle states under current authority.

### Truthful insights

Implement an explicit authorised rendered-open/view event separate from list/tree/search/preview/download-metadata reads. Define repeat-open counting and idempotency before implementation; prevent retries from multiplying counts. Preserve view events by original Auth identity and content/node ID. Current audience must govern reader access; historical author/viewer names and events must not transfer when an Agent relinks. Define the reporting denominator (current assigned active users versus historical recipients), date range and company timezone rather than guessing reference internals. Only actual events may feed percentages, last viewed and charts. A download can be labelled a download event, not proof that the file was read. Exact analytics and safe full-filter export should use the established complete-snapshot pattern; do not export only the displayed page.

Do not wire real notification/Chat/tag/task actions without separately implemented authorisation, explicit UI action and existing user permission for that feature. A future Quick Task shortcut can link to an authorised base/node; its completion remains separate from Knowledge Base view counts. There is no reference evidence for a native mandatory Knowledge Base read-confirmation prompt in these sources.

## Future Smart Group audience integration (no current contract change)

Current CT Alt Smart Groups are organisational **Agent records**, including unlinked profiles. They do not assign content or grant Auth access. Leave that released/current module and existing Chat/Updates fixed Auth audiences unchanged.

A future Knowledge Base assignment mode can explicitly choose `selected_users` or `smart_groups`, matching the verified base-level selector. Store the selected group IDs/rules identity as assignment sources; never silently turn their record-count preview into Auth IDs or a fixed recipient snapshot. For dynamic sources, re-evaluate currently matching active Agent records and then resolve only current linked active confirmed nonanonymous tenant accounts. Deduplicate Auth IDs. Unlinked/unavailable matches remain visible organisational statistics but confer no reader access. New eligible users gain access; users whose records stop matching lose current access; both behaviours need explicit tests.

Unknown fields, invalid rules, archived/missing groups or inactive parents need a defined fail-closed assignment state and an administrator repair flow. They must not broaden access to all users or fall back to a previous population without an explicit reviewed policy. Group deletion/reuse identity must not reconnect old assignments accidentally. A field/rule/population or linked eligibility change must invalidate audience pages and access caches. Fresh signed checks must re-evaluate audience access across text/search/file/insights as well as catalog visibility.

Relinking an Agent can change the future dynamically computed reader set because its **current linked eligible account** changed. This must not transfer prior file views, acknowledgements, Chat membership, Updates audiences, receipt ownership or authorship from one Auth actor to another. Preserve old Auth events and recheck the new actor independently. Static selected-user assignments continue to refer to the selected Auth actors regardless of Agent-record relinks.

The official assignment guide says mixed Smart Groups + Selected Users is available for Quick Tasks, Updates and Chat, but later includes Help Desk too. This is an internal source inconsistency. Knowledge Base is consistently described as **Smart Groups or Selected Users**. Do not claim mixed-source KB assignment is verified; if later added to CT Alt, document it as an extension. An Updates-style fixed-vs-dynamic group snapshot choice is specifically documented for Updates, not established for KB.

## Full parity gaps and decisions to track

- Templates and exact base activation/publish/draft/archive/delete scheduling workflow; granular/per-base administrators and administrator-as-reader semantics.
- Folder-level audience is explicitly unsupported by the reference; never add it under a parity claim.
- Limits and failure behaviour for hierarchy depth, sibling count, names, duplicate names, subtree moves, cross-base moves, folder deletion and historical insight retention.
- Full rich text (images/tables/highlights/spacing), video/image/PDF/Word previews, real files and quotas, multi-file uploads, versioning, range/download protection, malicious-content handling and all advertised file types.
- Persistent base ordering, sibling ordering, temporary column sorting and keyboard accessibility.
- Exact search scope/tokenisation/case/Unicode behaviour, file-name versus content search, all-base search and OCR. Verify before claiming more than base-scoped title/file-name search.
- Dynamic group assignments, published assignments from the Smart Groups page, protected All Users semantics, permissioned assignment catalog and per-feature mapping. These require a new separately reviewed integration, not a change to the current organizational-groups slice.
- Exact unique/repeated view semantics, event time, reporting denominator, last-month chart buckets, statistics on text/links versus documented folders/files, historical/inactive assignees, custom columns, filters and Excel export format.
- Read reminders, task shortcuts, Chat/tag/task actions, push/email notifications, AI Knowledge Base agent, offline use and mobile functionality. The starting guide links an AI assistant article, but its capabilities were not researched here and no AI service is proposed.
- Plan gates are competitor packaging evidence; no subscription/billing replica or paid resource is authorised. CT Alt must state its actual supported limits and free-resource constraints plainly.

## Acceptance evidence needed before release

Signed owner/admin management versus assigned/nonassigned manager/employee/foreign access; current company/member/Auth/management/audience revocation including delayed reads and old cookies; no list/search side effects; literal Unicode search and complete bounded population; safe text/links; revision/UUID/tree/order concurrency; no cycles/tenant crossover; parent lifecycle and unknown-write recovery; late path/base/filter/download/decoded-ACK departure fences; preserved workforce and populated Diary/Clock/Chat/TimeOff/Updates/Smart Groups rows/functions. For files, test authorisation both through the app and directly at storage and inspect only synthetic uploads/captures. For insights, test exact counts, repeat-event policy, distinct original actors and complete safe export. No hosted fixtures, notifications or real policy documents.
