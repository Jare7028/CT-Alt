## Delivered server contract

Owner/admin can create and edit drafts, publish, archive and restore. Plain text title/body, comments/reactions settings and optional read confirmation are explicit. A draft selects 1–500 distinct current confirmed nonanonymous active Auth-company members; publishing rechecks every selected member. Names are snapshots. Published content, audience and settings are immutable. Archive removes employee access and stops engagements; restore retains timestamps, comments and reactions. There is no delete, published edit or admin moderation in this slice.

Communication identity is the Auth user and current company membership, consistent with Chat. Agents do not control Updates identity: an agent-record relink alone neither grants nor removes this Auth user's audience. A newly linked Auth user does not inherit another user's recipient row, reaction or confirmation. Owner/admin management content/analytics authority is separate from actual recipient engagement: a nonrecipient admin cannot view-mark, confirm, like or comment.

`GET /api/updates` accepts `tenantId`, `view=feed|manage` (feed default), `status=all|draft|published|archived`, literal title `search` ≤100, `limit` 1–100 (default50), and opaque cursor. Feed shows currently published posts assigned to this actor. Counts are exact before selected status, honoring view/title search, with no directory-size truncation. Management includes draft/published/archived. Feed orders publication time/UUID descending; management orders creation time/UUID descending.

`GET /api/updates/roster` is owner/admin-only, with tenant, literal name search, bounded limit and opaque name/UUID ascending cursor. It searches the entire eligible Auth-membership roster, not only the first page. SQL performs Unicode lowercasing; the server preserves its opaque sort position without recomputing a possibly different JavaScript lowercase value. UI must retain selected names/IDs across searches and pages.

`GET /api/updates/[id]` returns post, management-only complete bounded selected recipients, and descending timestamp/UUID comments with `nextCommentsCursor`. Removed comments retain identity/history metadata but return an empty body. Comment capabilities are server-computed: active own comment, actual current recipient, published post, comments enabled. No management moderation is inferred.

`GET /api/updates/[id]/recipients` is owner/admin-only, accepts all/viewed/unviewed/confirmed/unconfirmed, and returns paged recipient statuses plus exact total/viewed/confirmed/likes/active-comments counts independent of the selected status/page. Detail/roster/analytics DTOs include `tenantId`, `actorId`, `role`; consumers must reject results for a different current identity/company/role.

All GETs are side-effect free: no view marks, reactions or confirmations. Only explicit `view` after an authorized detail opens records first-view time. `confirm` is a separate explicit action, available only when configured, and atomically records first view if absent. Repeated view/confirm keeps first timestamps. Likes/unlikes are current-actor state. Comment creation, own edit and own soft removal use server time and independent comment revisions. The UI must not equate a viewed post with a confirmed read.

`POST /api/updates` accepts `{tenantId,operationId,change}`, returns `{saved}`, validates strict action fields, same-origin requests and JSON ≤40KiB. API input/textarea limits are 160 title, 5000 body and 2000 comment UTF16 units; SQL also safely accepts direct signed RPC Unicode strings within its character limits. DTO validation accepts their corresponding doubled UTF16 bounds and enforces actual codepoint limits. No client timestamp, actor, tenant reassignment, privileged key or arbitrary payload field is accepted.

Draft create starts post revision1/content revision0; draft edit increments revision; publish increments revision and freezes content revision1; archive/restore increment revision without changing content. Engagements do not increment post/content revision; comment create starts revision1, own edit/remove increments its revision. Acknowledgements bind operation UUID/action/post/content and comment identity/revision; lifecycle acknowledgements bind expected post revision+1.

## Authorization, replay and concurrency

All new exposed tables have signed-user SELECT-only RLS and no direct browser writes. Three public RPCs are invokers; private definer helpers/mutations use an empty search path, fully qualified objects and current `auth.uid()` authority. PUBLIC/anon/authenticated/service_role EXECUTE defaults are explicitly revoked before intended authenticated grants. Private receipts are inaccessible and protected with RLS/default deny. The local runner models permissive hosted table and function defaults, so grant checks are meaningful.

A mutation locks current company/Auth/membership identity before authorization, then serializes post lifecycle and personal engagement on the post row; recipient rows are locked for personal operations. Initial recipient selection/publication locks member/Auth rows and checks current eligibility. UUID advisory serialization protects create and concurrent retries. Payload-bound receipts are actor/company scoped, transactional with mutation and audit.

Current owner/admin authority is required before management receipt lookup. An authorized same actor can acknowledge a prior management write after the post's state or recipients later change, without repeating it. Personal receipt lookup still requires current confirmed active company/member/Auth, current recipient, published post, content revision and enabled engagement setting; own comment identity is required for comment edit/removal replay. Archived posts, removed recipients, suspended users/company and revoked admin roles deny replay. A prior comment edit/removal receipt may acknowledge its old revision after a later own edit/removal, without repeating a write; fresh reads remain authoritative.

Each read is one stable signed invoker statement snapshot for counts/page/capabilities, followed by a fresh signed access RPC. It rechecks current actor/role/company and each returned post's current status/revision/content revision/current-recipient flag, including admin recipient feed authority. Read errors are 503, access failures 403, invalid requests/cursors400 and revision/retry conflict409; failure never turns into successful empty/zero data. Counts/engagement rows represent the initial statement snapshot. Unseen roster/member/engagement changes may occur subsequently; mutation eligibility is checked again. No read can guarantee authority will stay unchanged after its final successful recheck and delivery.

Cursors bind actor/company/read kind/role/filter/search/post/content and lifecycle revision where applicable. SQL preserves microseconds and UUID tie breakers; there is no unsafe JavaScript bigint conversion. Precise timestamp comparison and duplicated/incorrect page boundaries are rejected. All lists and recipient payloads are bounded.

Unknown writes require the reviewed recovery UI contract: persist only a marker scoped to actor/company, without title/body/comment/recipient fields; block new mutations while unknown; allow only exact same in-memory payload/UUID replay; require a successful fresh scoped read to release the lock; failed reads/access denials keep the lock. Navigation must not replay field payloads. Reads and controls require actor/company/post/request-generation fencing.
