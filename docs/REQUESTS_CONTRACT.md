# Requests kanban

The owner requested a persistent Requests kanban board and live demo data on 4 October 2026. Scope is general work requests, following the stated default after the optional type question received no reply. This is a custom workforce workflow styled consistently with the standard desktop reference, not a claim that Connecteam offers this exact board.

## Product behavior

A company-scoped board has New, In progress and Done columns with exact counts for the visible query and bounded per-column paging. Cards show actual title, description preview, priority (low/normal/high), optional due calendar date, requester and optional active linked assignee. Create, view/edit and move cards persist; native drag/drop has an equivalent keyboard-accessible status control. Search filters actual title/description. No messages, email or notifications are sent.

Owner/admin can read and manage all company requests, including assignment. Other current confirmed members can submit New unassigned requests and read their own requested or currently assigned records; they can move only their current assigned requests. A requester may edit their own unassigned New request; assignment and general triage remain owner/admin actions. Managers gain no extra company-wide request access by implication. Assignees must be active linked company user records with active memberships. Archive is optional only if implemented end-to-end; no delete button or pretend action.

All decisions come from current signed identity/membership, never caller-supplied user/role fields. Suspended company/user, anonymous/unconfirmed Auth, revoked membership, archived/relinked assignee and foreign-company access fail at the server/database. No unauthenticated/direct browser writes. RLS guards direct reads; audit visibility follows current request access. Private operation receipts have no direct authenticated/anonymous access.

Core establishes strict versioned DTO and change/query types before UI implementation. Required DTO scope: company metadata/timezone/current actor role/ID, capabilities, exact per-column counts and individually bounded pages/cursors, actual card IDs/revisions/requester/assignee/timestamps and permitted operations. Counts and rows share one authorised database snapshot. Sort/keyset retains microsecond precision and deterministic ID tie-break. Filter/cursor binding includes company/visible actor scope/status/search and rejects stale or mismatched scopes without silently losing records.

GET uses strict UUID/query parsing, bounded limits/search, no-store and current access checks. POST uses same-origin enforcement, streamed byte bound/strict UTF-8/strict JSON and schema, canonical positive revisions and generated UUID operation IDs. Mutations use current tenant/actor/target locks, exact expected revision and idempotent actor/company receipts. Receipt replay must recheck current permission before returning, reject a changed payload for the same operation ID, and never fabricate a second audit or card. Unknown payload fields, invalid transitions/dates/assignments and foreign IDs fail atomically.

## Browser integrity and acceptance

Preserve company/actor fences through stale reads, late acknowledgements and role changes. Clear private board/cards on current access denial; an older successful response must not restore them. One pending write keeps all conflicting mutations/recovery reads locked. A settled uncertain outcome supports exact in-memory retry with the same payload/UUID; session recovery markers must survive navigation/reload without embedding private payloads or unlocking on a failed recovery read. Reconciliation must establish a recorded receipt or a current authoritative state after the write fence; do not clear an unresolved marker from a pre-commit snapshot. No optimistic cross-column move before acknowledgement. Conflict reload preserves the user's text for review and never silently overwrites another revision. Validate returned write acknowledgement against the pending operation/action/card identity and expected result.

Meaningful checks cover tenant and role isolation, current revocation/assignment/relinking, populated upgrade retention, revision/idempotency/receipt races, per-column counts/paging/search, dates and byte/schema validation. Synthetic desktop tests cover drag/drop and keyboard movement, create/edit/assignment, search/paging, failed reads/writes, invalid ACK, held write, lost ACK/exact retry, reload markers and late company/role responses. Genuine local Auth/API/browser acceptance uses fresh owned loopback fixtures; no hosted fixtures except the separately authorised labelled demo seed. Whole check/build, appropriate retained SQL suites, independent review, exact CI and matching production READY are required before release.
