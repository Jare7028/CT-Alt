# Updates recipient CSV desktop review

This follow-up adds **Export recipients** to the existing owner/admin recipient-status panel. The public reference is Connecteam's [Tracking Engagement on Updates](https://help.connecteam.com/en/articles/6533885-how-to-track-engagement-on-updates), which describes individual viewed/not-viewed filters and exporting those results. The original public prose remains cached outside Git in `/tmp/connecteam-updates-research/6533885-how-to-track-engagement-on-updates.txt`. No private reference session or workforce data was used.

The button explains that it exports every recipient matching the selected status, including users beyond the displayed page. It sends only the company and selected status to the dedicated export endpoint; it does not accumulate loaded pages or include a cursor/limit. The signed server supplies one complete coherent snapshot of the fixed audience, bounded to 500 users. The CSV contains user name/ID and distinct viewed/confirmed statuses and UTC timestamps; it contains no private contact fields or comment bodies. Confirmation disabled is represented by the server as Not required. Existing list/search/detail/view tracking, draft management and exact UUID write/recovery behavior are retained.

Preparing the file shows a genuine busy state and disables duplicate export clicks. A successful browser download initiation shows a separate status message. The client validates the current actor/company/update/status/role headers, UTF-8 CSV media type and fixed attachment filename before decoding and again after decoding the Blob. The filename is generated from the selected update UUID. Both reported and decoded sizes are bounded to 1 MiB; an empty Blob is rejected. This bound permits the valid worst case of 500 names containing 100 Unicode emoji, with both precise timestamps, which exceeds 256,000 bytes. The Blob is downloaded through a temporary object URL and hidden download link; the link is removed and URL revoked after initiation.

Export is a scoped leaf read. Its abort controller participates in the existing mounted/request/generation fences. Closing analytics, changing status/post, navigating to another leaf, manually refreshing, changing company/actor/role, departing or starting a mutation aborts it. Both response-header and Blob-decode awaits recheck that the same analytics scope and controller remain current; a delayed result cannot download after leaving its scope. A synchronous pending-write guard also blocks a forced export click during POST. Current denial, malformed scope/CSV metadata, failed read or invalid body clears private Updates rows, analytics and editors via the existing access-clearing path and leaves changes locked until a successful fresh read. CSV rows and draft/comment fields are never persisted to recovery storage.
