## One attempt, proof and completion guard

1. Server validates multipart, current signed owner/admin and expected tree/revisions, buffers bounded bytes, computes actual SHA256/type/size locally. One signed private mutation reserve_file atomically allocates immutable attempt+permanent path+tombstone and consumes its sole outbound upload claim, under the normative lock order below. It records state='upload_attempted', claimedAt/deadline (fixed server10minutes), exact metadata/payload hash excluding proofs. First successful caller gets claimed=true; any sameUUID retry gets claimed=false and only the safe logical attempt/status. No receipt ever re-grants outbound upload. If claim acknowledgment is lost before outbound HTTP, quota remains charged and reconciliation/closure is required; never infer it is safe to retry bytes. No provider SDK automatic retries.

2. Only claimed=true server constructs upload-v1 HMAC and sends one raw signed-user POST object upload with x-upsert:false and exact immutable path. user_metadata contains {ct_alt:{v:'upload-v1',keyId,attemptId,operationId,proof}} only. HMAC message uses an explicit versioned canonical encoding implemented identically in server/SQL: ordered ASCII field names, canonical lowercase UUIDs, decimal byte count, lowercase SHA256, exact MIME, and decimal deadline milliseconds, each value UTF8 length-prefixed. Bind keyId, tenant/base/node/attempt, original actor, operation, path, bytes/hash/type/deadline. SQL recomputes from private stored attempt, not supplied metadata values; constant-time byte comparison where practical, no proof echoed or audited. Upload-v1 does not bind unknown future provider UUID; signed intent binds actual first accepted UUID at completion.

3. Storage INSERT RLS permits ONLY storage.object.upload, exact CT bucket/path/current original authenticated actor, owner_id, still-open unexpired claimed attempt, expected bytes/type and valid proof. Other operations including sign_upload_url/upload_signed/TUS/S3/upsert/copy/move/list/sign denied. Preflight uses provider placeholder version='1', metadata.contentLength and rolled-back INSERT; it must verify intent without consuming durable acceptance. Lease acquisition already persisted outside this rollback.

4. A narrow CT-bucket BEFORE INSERT/UPDATE trigger is mandatory because completeUpload is privileged. Every CT objects UPDATE is rejected, including ON CONFLICT fallback; existing finalized path immutable. At actual INSERT, provider version must canonical UUID (not placeholder1); service_role context AND storage.object.upload required, correct owner_id equals stored original actor independently of auth.uidNULL, exact user_metadata proof/metadata size/type validated. Acquire the normative locks below; confirm stored original actor still confirmed nonanonymous active company member owner/admin, existing same tree/revisions and deadline, state upload_attempted, no accepted version. Atomically bind first accepted provider objectID/version and mark uploaded_unverified. Reject late/duplicate/closed/expired/revoked completion. A preflight authenticated INSERT cannot mutate acceptance. Add an initially-deferred CT constraint trigger that rejects a persisted placeholder version='1' at transaction commit: genuine provider rolled-back permission testing never reaches it, while a direct signed SQL/RPC INSERT cannot commit the fake row. The immediate trigger accepts a real UUID only in service completion; direct signed real-version INSERT fails. Table grants/RLS also enforce provider operation/current scope. No authority cache, no application service key, no trigger-derived issuer from service auth.uid.

5. Provider writes physical random-version bytes before metadata finalize, so rejected late/duplicate finalize may leave bytes if provider cleanup fails. Failure/prior-version ObjectAdminDelete scheduling is observed machinery, not positive absence. Keep allocated charge forever in this increment; no claim that DB rollback rolled back physical bytes. ## Verified finalize and direct-RPC defense

After durably server-attested successful provider upload ONLY, the server performs fresh signed state lookup, finds exact accepted metadata/providerVersion and downloads authenticated exact path?versionId=<accepted UUID>. Bound stream verifies actual byte length, SHA256 and supported actual type; hash must equal reserve intent. It then computes finalize-v1 HMAC bound to actor/tenant/base/node/attempt/operation, accepted provider objectID/version, actual bytes/hash/type and short server verification deadline (60seconds), plus expected base/node revisions. Private finalize RPC recomputes against inaccessible key and stored attempt and rechecks current original actor owner/admin, company/tree/revisions, accepted exact provider identity and current time under same locks. Only this server-attested proof can finalize: direct authenticated RPC invented hash/size/type/proof must fail without audit/current-pointer/receipt changes. Proof never enters logical payloadHash/receipt/audit or DTO; it is ephemeral verification provenance. Receipt binds exact logical request metadata/bytes hash and original actor; prior receipt replay rechecks current authority before acknowledging, without repeating upload/finalize or rejecting solely because later unrelated management revision advanced. Fresh finalize after stale revisions must fail and close candidate, retaining old current version.

Finalize atomically creates file node/version or replaces pointer, increments aggregate and targeted management revisions once and writes one audit/UUID receipt. A state already finalized returns original safe acknowledgment after current authority, never re-verifies/uploads. Rendered revisions and exact pointer/proof fences remain for fresh finalize. Separate reconciliation returns field-free known-status evidence or safe current attempt metadata only to current original owner/admin; personal views continue existing field-free reconcile contract. A new Auth actor/other admin does not inherit original operation/byte retry identity.

## Retention and safe cleanup decision

First increment retains all finalized/superseded versions and all allocated budget. Archive/move do not delete bytes or free quota. An explicit owner/admin cleanup may target only CLOSED noncurrent attempts with KNOWN accepted exact providerVersion; no unknown-version path deletion, no bulk delete, no SQL storage.objects delete. Permanently close under attempt mutex before invoking provider. DELETE exact path?versionId=<known UUID> with original current signed actor, ONLY operation storage.object.delete; RLS checks current owner/admin plus closed noncurrent attempt/provider version. Metadata trigger must permit this narrow DELETE under existing provider delete-query guard but never permit UPDATE. Single route returns only Successfully deleted; delete_many returns user_metadata and is permanently denied. Deleted attempt remains tombstone with charge. Fresh signed cleanup reconciliation distinguishes acknowledgment from uncertainty; any error/no row/404/remove200[] remains uncertain and never frees quota. No product cleanup of unrecorded physical orphans; their reservation charge remains and root-operated provider maintenance is separate future work.

This deliberately stops short of positive physical-absence/quota reclaim. Even genuine single DELETE200 indicates completed backend deletion for its known version in reviewed provider code, but does not prove absence of other preflight attempt versions/orphans at that path. First slice never turns any such response into quota credit. UI explicitly warns failed/unknown uploads and replacements can consume retained budget. Provider cleanup retries/background jobs not implemented or implied.

## Normative integration decisions (4 October 2026)

These decisions supersede ambiguous wording above. User authorization already covers this implementation; no hosted configuration has yet changed.

**Locks.** Existing actor+operation advisory (hash seed63) FIRST; existing company advisory (seed64) SECOND; deployment allocation advisory/row THIRD; base row, node row when present, attempt row, version row LAST in that order. Provider completion enters while it already holds a Storage object lock; its trigger acquires only this ordered application lock chain. No application RPC ever acquires Storage row/advisory locks afterward, including implicit FK locks. Provider object ID/version are checked immutable plain identity values, NOT foreign keys into storage.objects. Finalize uses ordinary MVCC reads of exact accepted provider identity, serializing through the attempt. Close commits before outbound deletion. Closed attempts never reopen. Cleanup DELETE enters through the provider lock order and current private closed/noncurrent validation. Never make a reverse Storage lock path.

**Global budgets.** Exactly100MiB positive-byte lifetime allocation over this CT Alt deployment, maximum4,096 attempts globally and2,048 attempts per company, including every failed/unknown/tombstoned attempt. Finalized versions are bounded by those attempts. All counters only increase. Reserve takes the global allocation mutex even for different companies. UI reports only its own company allocations and own state counts, the published global cap and an explicit unavailable-budget result; no other company identities or allocations. No capacity/reclaim promise.

**Storage SELECT.** Exact object.get_authenticated only: (a) uploaded_unverified/provider_succeeded candidate, current original confirmed nonanonymous active owner/admin only, exact accepted ID/version and open nonexpired attempt, even though a create node is pending; (b) finalized CURRENT product version, current owner/admin management access or current published assigned reader with active full path. Superseded/closed/unknown/orphan objects are never audience-readable. Cleanup-only SELECT and DELETE permit exact permanently closed, noncurrent KNOWN accepted ID/version, current confirmed nonanonymous owner/admin, only object.delete. object.delete_many/info/list/sign/sign_upload_url/TUS/S3/copy/move/upsert and every object UPDATE are denied. Other buckets early-return before any CT proof/key/private lookup and remain unchanged.

**Provider uncertainty.** Pinned provider may schedule a physical ObjectAdminDelete after an uncertain metadata COMMIT acknowledgment. A later successful metadata/GET reconciliation is insufficient provenance. Only an unequivocal successful bounded provider upload HTTP response with validated exact returned object ID/path allows the server to mint a distinct provider-success-v1 HMAC, binding original actor/operation/attempt/accepted object/version/intent and a short server deadline. A signed RPC durably records that attestation as provider_succeeded. Direct authenticated callers cannot forge it. Browser loss of the application's response is recoverable after this durable record; server-to-provider upload uncertainty or loss before success is durably recorded requires permanent close/retained allocation and NEVER promotion or second upload. An uncertain success-recording RPC may reconcile its durable state; it cannot invent the proof from row/GET alone after the original successful response has been lost. Provider_succeeded is required for finalize-v1. Verification/finalize retries only occur after that durable success and all fresh gates. No test need reproduce a hypothetical network COMMIT loss to enforce this conservative prohibition.

**Role/ACL.** Trigger SECURITY DEFINER current_user is its owner; completion issuer must use reviewed non-user-forgeable actual SET ROLE context (current_setting('role'), supported by provider runtime fixture), operation, valid HMAC and original owner/current membership. JWTrole alone is insufficient. Revoke default PUBLIC/anon/authenticated/service_role execute/table grants, then allow only explicit authenticated invoker public wrappers and narrowly current-authorized private read/mutation helpers. Guard/key/signature/completion internals have no direct signed/browser execute. Private key has no public exporter/signing oracle. Existing schema grants/defaults and other bucket policies unchanged.

**Protocol/types.** Strict metadata create union: {tenantId,operationId,baseId,mode:'create',expectedBaseRevision,parentId,name,description,filename}; replace union: {tenantId,operationId,baseId,mode:'replace',expectedBaseRevision,nodeId,expectedNodeRevision,name,description,filename}. Create requires an existing active folder, following released root-folder rules. Original filename rejects CR/LF/NUL/unpaired surrogates, cap255 UTF16/1024UTF8. Canonical media types application/pdf,text/plain,text/csv,image/png,image/jpeg; filename extension plus strict sniff determines type. Empty/application/octet-stream and application/vnd.ms-excel only for.csv are permitted declared aliases if sniff/extension agree; reject any other conflicting declared MIME. Empty bodies rejected. Positive file sizes bounded2MiB. Metadata/form transport limits and duplicate/unknown fields strictly enforced.

Public file types live in lib/knowledge-base-file-types.ts. Existing KnowledgeNode gains file kind and optional currentFile metadata: REQUIRED on file, absent on all other kinds, preserving other-node JSON. currentFile fields versionId,filename,mediaType,bytes,sha256,uploadedAt,uploaderName. No path/provider proof/metadata/owner tokens. File operation action='save_file'. Safe result scope tenantId/actorId/currentrole/operationId/baseId/nodeId and integer current released KB revisions (1..2147483647); attemptRevision is integer positive and advances on each durable transition. Server internal DTO can carry immutable path/accepted provider IDs only after fresh original-actor authorization, never public browser DTO. Reconcile public DTO has status not_recorded|upload_attempted|uploaded_unverified|provider_succeeded|finalized|closed|cleanup_acknowledged and capabilities canFinalize/canClose; no outbound-upload capability. Old markers contain only action+UUID under existing actor/company key. New unauthenticated/different actor/denied recovery stays locked. Stale fresh finalize must persist CLOSED via a returned conflict result, not a raised exception rolling closure back; old pointer retained. Original receipt replay checks current resource authority first. Cleanup by another current admin uses a separate own operation/audit, never inherits uploader identity.

Binary download responses carry private no-store, attachment, nosniff, exact bounded Content-Length and CT product version/base/node/tenant/actor identity headers. UI validates these plus current leaf, actor/company, mount/epoch, view and requested version AFTER body decoding before creating a local object URL. Navigation/unmount/revocation aborts and clears private bytes/URLs; no refresh or recovery resurrects bytes. Explicit rendered file detail creates the existing view event; download never creates another event. Replacement controls keep the previous current version until successful finalize.

**Fixture/shared files.** Genuine Storage74 migrations with actual current provider runtime must precede filesSQL for the new full real-Auth acceptance runner. Historical offline SQL suites must retain their meaningful behavior and exact recorded baselines; do not manufacture minimal Storage objects as integration evidence. The integrator owns coordination of historical-runner migration ordering and CI.
