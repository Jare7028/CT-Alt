# Day and Week Templates proposed contract

This is an implementation contract, not a delivery or hosted-release claim. It extends merged minute-only hours main `b1be26b`, tree `5bf56dd`; all 23 applied migrations, legacy scheduler functions/APIs, displayed publication, single-shift templates and their recovery remain unchanged. The implementation is under verification; this document does not claim a hosted release.

The official [Schedule Templates guide](https://help.connecteam.com/en/articles/3524929-schedule-templates), updated 17 August 2026 and publicly read 4 October 2026, documents saving filtered days/weeks, loading, preview, title-only editing, deletion, and choosing Add or Replace when shifts already exist. Loaded shifts require separate publication. Public previews and loading images strongly support preserving assignments. The guide does not resolve detailed replacement, interval, timezone, assignment-remapping or inactive-worker rules. Historical public images do not establish exact current authenticated pixels. Advanced Operations Hub entitlement is documented; current free/trial availability remains unverified. Original CT Alt code/branding and synthetic public fixtures are required; no competitor images or private research artifacts enter Git.

## First delivered boundary

Company owners/admins and managers currently delegated to the schedule can save a reviewed displayed Day or Week as an immutable assigned-shift snapshot; list/search/page Days and Weeks; inspect a read-only preview; rename the title; tombstone the template; and Add its whole batch to another date in the same schedule as new private drafts. Saving accepts mixed draft/published source shifts and past/future dates. It never changes their status, assignments or history. Later source edits do not modify a saved snapshot. Templates retain actual directory Agent IDs, not names as identity; directory-only workers need no Auth accounts.

Only Add is implemented in this bounded increment. The official guide documents an Add-versus-Replace choice, but its exact dialog labels and geometry remain unverified. Do not invent explanatory replacement copy, present a disabled control as working Replace or call Add replacement. This remaining functional parity gap must be recorded outside the ordinary product flow. Replace requires a separately reviewed retention/cancellation design because existing shift references, publication and audit history cannot be safely hard-deleted. Cross-schedule copying, worker substitution, open/group shifts, recurrence, drag/drop, notifications and editable snapshot contents remain outside this increment. No new accounts, invitations, messages or notifications are created.

## Source period and exact capture

A Day source anchor is its local calendar date in the current schedule timezone. A Week anchor is the Monday shown by the existing scheduler and covers seven local dates. CT Alt currently has fixed Monday weeks; configurable week start is a separate gap. Reject a supplied Week date that is not Monday rather than silently moving it. Dates are strict real Gregorian `YYYY-MM-DD` values within the resolver's supported years; avoid JavaScript parsing or UTC date arithmetic to determine local days.

Source selection uses positive instant overlap with the half-open local period `[start boundary, following boundary)`, the current job/status filters and worker-name search. Both local midnight boundaries (anchor and anchor +1/+7 dates) must resolve through the unchanged timestamp helper with occurrence `''`, and both their local wall dates and resolved UTC instants must stay within AD years `0001..9999`, including the exclusive following boundary. A gap, ambiguous midnight, skipped boundary date or out-of-domain boundary rejects Source review/Save actionably; never guess an occurrence or shift a midnight. Thus a source period whose following boundary reaches year 10000 is unsupported even if individual shifts remain in year 9999. A skipped interior Week date is permitted when both boundaries are valid. This strict boundary limitation and the overlap/search policy are explicit CT Alt choices, unverified vendor semantics. Deduplicate a shift appearing in two cells by UUID. A shift ending exactly at the beginning or beginning exactly at the end is excluded. Capture a complete intersecting overnight shift, including its part outside the displayed period; never clip it or create separate entries for its cells.

Save first requires an authoritative read-only Source review. The legacy calendar's JavaScript `Date`/`hoursOn` uses millisecond precision and may omit a one-microsecond intersecting edge; its displayed set is not an exact source selector. PostgreSQL selects the complete microsecond-accurate filtered set using authoritative literal Unicode search semantics. The first Source review response returns all compact `{id,revision}` selectors (up to 5,000), a `sourceReviewDigest`, exact counts and at most 100 rich source rows. Later pages omit selectors and carry the same digest. The UI freezes that returned complete set/digest as the source of truth, rather than inferring completeness from loaded pages or legacy cards. This authoritative source review runs automatically; it is a protocol step, not an additional visible Review button, review page or checkbox before naming and saving a template.

The save confirmation freezes schedule ID/revision, kind, source anchor, filter descriptor, source timezone, complete selectors and digest. Save recomputes the whole authorized source scope/digest under locks and requires exact set equality, current revisions, same tenant/schedule and a nonempty result before copying persisted fields. No client-provided recipe contents are accepted. Any source fields/labels relevant to the snapshot, timezone/settings, permissions, filters or anchor changing invalidates the review. Source rows are locked before capture; no late source change may produce a different successful snapshot.

Source eligibility differs from loading: a historical snapshot may contain a now-inactive worker that the manager can still inspect. Save records that history without pretending it is loadable. Add always checks current eligibility. Captured assignment/shift/job names and job color support an honest historical preview; separate current labels/availability must not overwrite that captured copy. Generated drafts reference the existing current job, so their displayed color/name follows that job. Captured/current comparison remains internal; do not add explanatory label-comparison panels to the normal reference preview. Independent per-shift color does not exist in CT Alt and is not invented here.

## Immutable schema and precision

Use new schedule-scoped period metadata, entry, audit and private operation tables; do not change the minute-based single-shift recipe schema. Proposed metadata: ID, tenant/schedule, kind (`day` or `week`), title, source anchor/timezone, source schedule revision, captured filter descriptor, immutable entry/user counts and original elapsed microsecond total, revision, creator/created time, updated time and deletion time. Title is trimmed, 1–100 UTF16 units, valid Unicode and control-free, using the existing naming conventions. Rename and tombstone increment the template revision and schedule revision. Entries never change after creation, including after rename/delete.

Each entry has a stable zero-based index, source shift UUID/revision/status, original start/end UTC strings retaining PostgreSQL microseconds, assigned Agent ID and captured names, job ID/name/color, title, and independent start/end local date offsets and microseconds since local midnight. Source shift UUIDs are provenance with **no foreign key to legacy rota_shifts**. Captured worker/job IDs also remain provenance without new foreign keys to legacy agents/jobs that would block their existing deletion after source shifts/rosters are removed. Only the verified writer may insert: direct new-table INSERT/UPDATE/DELETE grants are revoked. It authoritatively validates same-tenant/schedule references at capture/apply; new entry parent tenant/schedule/template composite FKs enforce internal boundaries. The owning metadata schedule FK is compatible with its existing archive-only lifecycle. Later source/entity edits/deletion cannot rewrite/erase snapshots or become blocked by this feature; authorized historical preview still shows captured names/colors while Add is blocked for missing current entities.

Captured raw combined Agent labels accept at most 401 UTF16 units, job labels 200 and source shift titles 200. Within these bounds, retain valid Unicode, newlines, controls and outer spaces exactly; the control-free trimmed template-title rule does not apply to historical captured fields. Existing Agent/job checks bound trimmed names and can permit arbitrarily long outer spaces, so source review and Save reject an out-of-bound captured value atomically with an actionable explanation, without normalization or changes to legacy constraints or rows. These are CT Alt storage/response limits whose vendor equivalent is unverified. Final fixtures must accept ordinary Unicode maxima, reject oversized yet legacy-valid outer spaces, and prove 100 rich rows with worst escaping plus all 5,000 compact selectors fit the 1 MiB first-response bound.

Current availability labels, visible commitment labels and labels retained in newly generated history use a bounded internal presentation rule: apply PostgreSQL's default `btrim` (ASCII spaces) separately to current first name, last name and job name, then join first and last with one space. Existing trimmed-name bounds keep combined current Agent labels within 401 UTF16 units and job labels within 200, while preserving valid controls/newlines inside those bounds. This current-label presentation never normalizes the raw historical source snapshot, changes an entity ID/title/time, or prevents its authorized historical preview after a later raw name grows. This documented internal distinction does not require extra product guidance or a comparison panel; unsupported raw source capture remains an actionable rejection.

**Retain seconds and all six PostgreSQL fractional digits.** A local clock integer is in `0..86_399_999_999`; it fits safely in a JavaScript integer, as does the whole 5,000-entry elapsed-microsecond sum (at most `432_000_000_000_000`). Capture and timezone conversion occur in PostgreSQL from original timestamps. JavaScript `Date`, millisecond serialization, minute truncation and floating point epoch arithmetic must not determine stored endpoint precision. Canonical UTC strings are `YYYY-MM-DDTHH:mm:ss.ffffffZ`, preserving fractional digits in the database and typed protocol. Product clocks remain minute-only, preserving the current project's `09:00–17:00` presentation; duration totals display `HH:mm`. The user explicitly prohibited decimals and fractional clock lines, not mandated a vendor 24-hour locale. Do not expose seconds, fractional seconds, decimal hours, UTC endpoint text or technical precision details. This presentation never truncates the stored snapshot, changes generated instants or affects receipt validation. The proposed schema therefore needs no normalization consent. If implementation cannot retain this precision, stop and review an explicit per-source normalization preview/consent contract; never silently round historical data.

Supported endpoint dates are AD years `0001..9999` in both the exact local wall timestamp and canonical UTC instant. Source review/Save rejects any source endpoint outside either domain with an actionable explanation, retaining existing source rows unchanged. Target endpoints outside either domain produce stable `unsupported_endpoint` blockers under a coherent plan digest and deny the complete Add. This includes carry-in/out offsets or timezone conversion across the range boundary; never drop a BC era, silently change a year or serialize unsupported extended years. This is an explicit CT Alt limitation, unverified against the vendor, and does not reduce precision or alter supported historical timezone offsets elsewhere.

Offsets are the difference between each endpoint's local date and the source anchor, rather than an elapsed-hour quotient. Day entries accept offsets `-2..2`; Week entries `-2..8`, with exact source-period overlap independently proved. A shift crossing the period's beginning commonly has start offset `-1`; a late Sunday shift crossing two local midnights can retain end offset `8` rather than being clipped at the week end. These bounds cover the scheduler's existing maximum 24 elapsed-hour shifts and overnight/date-line edge cases without requiring wall endpoints to be monotonically ordered. Reject unsupported offsets explicitly. Preserve the complete endpoints and their relation, including a historical transition where local end precedes local start. Source UTC instants remain authoritative provenance; ambiguous source endpoints must round-trip to their original instant. Do not guess an interior occurrence if a historical timezone has more candidates than the supported earlier/later resolver can identify.

## Target date, timezone and complete preflight

Add is same-schedule only. A Day target anchor is the chosen local date; a Week target anchor must be Monday. It maps each saved start/end date offset to that target anchor and keeps the captured local clock microseconds. Target instants use the schedule's **current** supported timezone. The server preflight retains source/target timezone, anchors, full carry-in/out endpoints, assignments and exact elapsed durations. Ordinary product preview shows the assigned day/week layout and minute-only clocks; do not add timezone/debug paragraphs, raw UTC endpoints or precision lines. Exact template-specific timezone UI remains unverified by the official references. Historical source offsets remain intact server-side, but the preview uses only its Day column or Monday–Sunday columns. Never add “1 day before/after” columns or carry-in/out badges; clip card placement to the visible grid without clipping stored endpoints. This preserves wall endpoints; source elapsed duration is not promised across DST. Generic vendor timezone guidance does not establish this precise period-template policy.

Resolve every endpoint with exact PostgreSQL round-trip validation using the unchanged `workforce_private.rota_template_instant(timestamp,text,text)` helper. Its timestamp input already retains seconds/microseconds; only the individual-template caller is minute-based. Construct the full local timestamp from the exact stored offset/clock, never replace the applied helper. It samples offsets within ±36 hours every six hours and verifies the exact wall timestamp. Preflight can catch its gap/fold SQLSTATEs into paged diagnostics without creating shifts. Skipped local dates/times are errors. Repeated target times require an explicit earlier/later choice for that endpoint; unambiguous endpoints reject irrelevant occurrence overrides. Sparse choices use stable entry indexes with optional `start`/`end` values (`earlier` or `later`), unique by index. Defaults do not silently select an ambiguous occurrence. Each resolved shift must have positive duration no greater than 24 elapsed hours. A gap, unresolved fold, unsupported multiplicity/date/zone or invalid duration rejects the complete Add, even if thousands of other entries are valid.

All assigned workers must still exist, be active and be on this schedule's roster. Linked workers must retain active company membership; directory-only workers remain allowed. Jobs must currently belong to the same schedule. Current actor Auth/confirmed membership, role/delegation and schedule active status are rechecked. Preview may show unavailable entries with actionable reasons, but cannot report a loadable plan with skipped/reassigned rows. An archived schedule permits authorized catalog/historical preview and recovery; Add/save/rename/delete are denied. No worker remapping is implemented.

Whole-batch preflight detects both internal batch overlaps and positive overlap with all existing company commitments for each assigned worker, including drafts, published shifts and archived schedules. Adjacency is allowed. Public output reports the exact count of affected template entries and per-entry internal/existing-conflict booleans. Existing commitment detail is restricted by the unchanged legacy shift-read predicate and current permissions: `visibleCommitmentCount` is the exact count of distinct **visible** intersecting commitments and only those rows are paged. Owners/admins can see all eligible commitments; a manager of schedule A must never receive inaccessible schedule B IDs, revisions, endpoints, status, labels or counts. The only indication of inaccessible conflicts is opaque `hasHiddenConflicts: true`; no total commitment count or per-entry hidden count may reveal their quantity. Overlap authorization remains bound to the reviewed plan without granting additional read access. The final user-initiated Load template action can supply the approved Add acknowledgement; an extra overlap checkbox or technical conflict-review screen is not supported by the inspected vendor references. Never bypass the existing database conflict/digest checks or fabricate an affirmative user action.

Page affected entries and distinct visible commitments; do not enumerate/count overlap pairs or label a first page as complete. Internal booleans use a sorted per-worker sweep (previous maximum end/next minimum start), and external commitments use indexed/merged interval scans. New or changed conflicts or visibility invalidate the plan. All 5,000 entries with identical overlapping times must remain bounded in time/memory rather than generating 12.5 million pair rows.

Every target preview returns a stable `planDigest`, including blocked plans with `canAdd: false` and exact blocker totals. Blocked-plan pages remain coherent while the same state/choices hold; absence of a loadable plan must not prevent diagnostic pagination. The canonical digest is database SHA256 binding actor/tenant/schedule, current schedule revision/timezone/status, template identity/revision, target anchor, occurrence choices, all ordered generated tuples or unresolved-endpoint diagnostics, current eligibility, safe quota blockers/known requirements/authorized counts (never hidden raw usage), current read visibility and the exact distinct intersecting commitment IDs/revisions/endpoints/status. **Full hidden commitment tuples remain server-only digest inputs**, never public payloads. Generated tuples implicitly bind every internal conflict without pair enumeration. The digest is a coherence check, not authorization, and needs no secret, environment configuration or paid service. Add recomputes the entire plan under locks, requires `canAdd: true` and exact digest equality, and validates explicit consent for reviewed conflicts. No private receipt is written by preview. An unrelated commitment outside affected workers/intervals need not invalidate the plan; changed conflicts or visibility must. Capacity is checked again during the write, not trusted from preview.

## Bounds and paging

These are proposed CT Alt bounds, not vendor quotas:

- Save and Add support **1–5,000 entries** in one atomic operation. The API streams at most **512 KiB** with fatal UTF8, decoded duplicate-key rejection and strict schemas. Save sends source IDs/revisions, not full recipes; its maximum supported payload must be tested with all 5,000 highest allowed revisions. Add sends a template reference, target anchor, plan fingerprint, overlap acknowledgement and sparse occurrence choices. A maximum all-fold choice payload must also fit 512 KiB. Never truncate/split a successful batch.
- Four independent persisted retained-storage caps: **500 metadata rows per schedule**, **20,000 source entries per company**, **20,000 private operation records per company** (including `closed_absent`), and **20,000 generated immutable history links per company** (including deleted generated shifts). Tombstones count; repeated Add/delete cannot bypass the generated-link budget. Check applicable capacity under the tenant mutex before a new mutation/closure. Existing receipt lookup/recovery precedes quota checks, so recorded results remain recoverable when full. A new absence closure unable to reserve its operation row returns an error, never authoritative absence. A single 5,000-entry snapshot/batch is supported when its applicable budgets permit it. Capacity errors and preview totals are truthful; no automatic garbage collection/history deletion frees storage.
- Capacity/budget DTOs in Source review, catalog and target reads are role-discriminated; historical preview needs no budget field, and any future budget field must obey the same privacy rules. Current owner/admin receives `companyUsageVisible:true` and exact four company usage numbers (live shifts, retained source entries, private operations and generated links). A delegated manager receives `companyUsageVisible:false` with **all four company fields null**, never zero, while metadata usage for the current manageable schedule remains exact. Restricted users receive static limits, required entry count and opaque quota blocker/canAdd information, but no company used/remaining numbers through counts, errors, pages or cursors. Hidden raw company usage also must **not enter a public unkeyed digest**: low-entropy counters could be guessed when other inputs are known. Bind quota blockers/canAdd, known requirements/static limits and authorized visible counts instead. Raw hidden usage is a private fresh write check only; unrelated usage changes while capacity remains adequate need not invalidate Add. Server validators check the discriminator against fresh current role; the UI does not infer free capacity from null.
- Catalog pages are 1–100, default 30, with literal title search and kind filtering. Exact totals and page rows share one database statement snapshot. Catalog carries title/kind/created date/true entry/user counts, without embedded full entries. Stable ordering is normalized title under `C` collation, then UUID, like single templates. Keyset cursors bind tenant, actor, schedule revision, kind/search and those exact ordering keys; rename invalidates an old page cursor.
- Source review's first response has an explicit **1 MiB** encoded response bound covering all compact selectors plus its 100 rich rows; it is not a full 5,000-entry rich preview. Subsequent source pages omit selectors. Historical/target entry, invalid/affected-entry and distinct **visible** commitment pages are 1–100, default 100, with independent cursors and exact authorized totals. Order entries by stable index and commitments by UUID. Never leak hidden fields/counts through diagnostics/cursors. A 5,000-entry rich preview is transported in pages, never represented by a truncated first page with falsely complete totals. Cursors bind current actor/tenant/schedule/template revision, mode/target/choices/sourceReviewDigest or planDigest and position. Revalidate the full plan and current visibility/permission for every page; discard combined pages when the digest changes. Catalog access or possession of a cursor is not permission for deep entry reads.
- Add cannot grow all company shifts beyond the existing 5,000-shift whole-read capacity, counting all schedules/statuses. It never subtracts old shifts, even those outside the viewed period. A 5,000-entry load into an empty company is allowed; the same batch into a company with one retained shift fails completely. Preview reports requirements and authorized capacity honestly; restricted managers get opaque quota blockers rather than hidden company usage/remaining counts.

## Public API outline

New `/api/rota-period-templates` keeps existing endpoints intact. The approved conceptual `lib/rota-period-template-types.ts` exports kind/filter/selector/occurrence types; catalog/history/source/target queries; mutation/recovery queries; and catalog/history/source/target/saved/reconciliation response types. UUIDs normalize lowercase; request revisions are `1..INT_MAX-1`, results `1..INT_MAX`. Filters are `{jobId: uuid|null,status:'all'|'draft'|'published',workerSearch: validText<=100}`. Sparse occurrence rows are `{index:0..4999,start?:'earlier'|'later',end?:'earlier'|'later'}`, at least one endpoint, unique index and no irrelevant override. All shapes are strict; bounded text follows existing Unicode/UTF16 conventions.

`GET` catalog is `{tenantId,scheduleId,kind,q?,limit?,cursor?}` and returns schema version, tenant/actor identity, current schedule access, catalog rows and exact paging metadata, plus role-discriminated `capacity`, `canEdit` and `editBlockers` (`schedule_archived|operation_capacity`). Known blockers disable new Rename/Delete operations while recorded recovery remains available. Historical detail uses `{mode:'history',tenantId,scheduleId,templateId,templateRevision,limit?,cursor?}` and returns paged immutable entries plus fresh current availability; it never falls back to unvalidated catalog data.

`POST {mode:'source-preview',tenantId,scheduleId,scheduleRevision,kind,sourceAnchor,sourceFilters,limit?,cursor?}` is read-only and server-authoritative. The response is a strict discriminated union: initial `firstPage: true` without a request cursor returns complete sorted compact selectors, `sourceReviewDigest`, authoritative source scope/timezone, exact totals and at most 100 rich entries. Later `firstPage: false` MUST omit selectors and retains the same digest/scope/count bound into its cursor. The UI freezes the complete first-response selector set rather than reconstructing it from pages. The source digest includes all captured persisted fields/revisions/worker+job labels/color/timezone/anchor/filter, not just IDs. Source review also returns role-discriminated `capacity`, `canSave` and `saveBlockers` (`schedule_archived|metadata_capacity|entry_capacity|operation_capacity`). Known budget/archive blockers disable Save before an operation identity is sent. The source digest excludes raw quota usage for every role because usage is not a captured field; Save freshly checks budget under locks.

`POST {mode:'preview',tenantId,scheduleId,scheduleRevision,templateId,templateRevision,targetAnchor,occurrences,pageKind,limit?,cursor?}` is read-only; pageKind is `entries|blocked|affected|visibleCommitments`. It validates the entire target plan and always returns `planDigest`, `canAdd`, exact `blockedEntryCount`/`affectedEntryCount`/`visibleCommitmentCount`, opaque `hasHiddenConflicts`, whole totals and role-discriminated capacity/archival blockers with bounded authorized pages. Blocked entries are pageable under the same stable digest. Fresh permission/visibility checks precede every returned page. No hidden commitment tuples/counts or restricted company usage numbers are exposed.

`POST {tenantId,operationId,change}` handles strict `save|rename|delete|add` changes. All require `schedule_id`/`schedule_revision`. Save adds `kind,title,source_anchor,source_zone,source_filters,source_review_digest,sources` (the complete frozen server-returned selectors). Other actions add `template_id`/`template_revision`; Rename changes title only. Add supplies `target_anchor,occurrences,plan_digest,expected_entry_count,allow_overlap`, including consent for opaque hidden conflicts. Expected count must equal immutable stored count independently in SQL and the exact acknowledgement count in API. Add recomputes `canAdd: true`; a blocked digest is valid for paging, never sufficient to mutate. Unknown fields/types, duplicate IDs/indexes and mismatched kind/anchor/scope fail independently in API and SQL.

Saved common fields are `schemaVersion,tenantId,actorId,operationId,action,template_id,template_revision,schedule_id,schedule_revision,entry_count`. Add returns complete `generated:[{index,id,revision:1}]` with exactly indexes `0..N-1`, unique IDs/full count, and `plan_digest`; the API validates every index/ID/revision and the reviewed digest. Other actions return `generated:[]`/`plan_digest:null`. Save count equals source selector count and starts template revision 1; Rename/Delete advance template revision once; Add preserves it. A new commit advances schedule revision once; replay does not. No acknowledgement is inferred from only a count.

Add creates precisely one new draft per stored entry and one batch audit. Immutable history links retain each complete created target tuple, source entry/index, worker/job IDs and captured target labels, title, exact endpoints and initial revision 1. Generated shift/worker/job UUIDs are independently validated provenance without new FKs to legacy shifts/agents/jobs, preserving permitted deletion while retaining history; parent FKs refer only to the new audit/entry boundaries. This does not remove the old single-template audit FK restriction. Original publication timestamps/IDs and attendance/audit history are never copied. Do not change legacy rota_audit's action constraint: keep detailed new actions in the new period audit.

`POST {mode:'reconcile',tenantId,operationId,action,scheduleId,templateId}` returns a strict actor-bound `recorded|not_recorded` union, complete Saved only when recorded. Template ID is null only for Save. Response envelopes validate every returned index/shift ID/count/scope/revision/action/digest. Original recorded results remain valid after later revisions or permitted source/generated entity deletion: validate immutable receipts/history, not current shift existence/equality. All endpoints use private/no-store; API signed identity and current database permission are rechecked before returning catalog, deep preview, acknowledgement or recovery. Revocation clears protected UI state and fences delayed successful responses.

## Atomicity, recovery and retention

Use operation-UUID lock, then the existing tenant mutex, current actor Auth/membership, schedule/delegation, template and ordered source/target worker/job/roster/membership/commitment locks. Match existing writer lock order to avoid deadlocks. Whole-plan verification, capacity, creation of every draft, audit links, schedule revision and receipt commit in one transaction. Any invalid entry or serialization failure leaves all old rows, drafts, audits and receipt state unchanged. Cross-schedule existing writers serialize through the same tenant mutex.

Private operation records have no browser grants. They bind tenant/actor/UUID, canonical immutable payload hash, action and original schedule/template target. Exact replay returns the original bounded acknowledgement with no extra shifts/audit/revision; mismatched payload/scope conflicts. Existing recorded/closed operation lookup occurs before new-operation quota enforcement. Recovery serializes with the original write and returns either its durable result or a durably reserved `closed_absent`, preventing a delayed original request from committing. At the 20,000-operation cap a new absent closure cannot be reserved: return a quota error, never `not-recorded`. Recorded recovery remains available at full quota with current permission. Failed/denied/quota-blocked recovery is not proof of absence. Current permission loss blocks receipt disclosure; authorized recovery remains possible after archival/template tombstoning. Later authorized mutations do not invalidate a recorded acknowledgement, so fresh access checks must not require current revision equality to its old revision.

Before sending, the UI persists only an actor/tenant-scoped operation identity/action/schedule/template marker, with no names, worker IDs, recipes or source shift arrays. In-memory payload remains immutable while saving; double submission and competing local writes are blocked. Storage failure prevents sending. Lost/unverifiable acknowledgement or a new-operation quota error can leave the operation uncertain until verified recovery/closure, including after navigation/reload. A quota-blocked closure retains the lock and explains that absence could not be established. Reload never creates a new UUID or silently resends Add. Authoritative absence permits an explicit new review/operation, not a delayed closed write. Permission denial clears protected content without treating the operation as absent.

Deleting a template is a tombstone: retained immutable entries, audit links, operation results and generated drafts/published shifts stay intact. Catalog excludes tombstones. Ordinary preview of a tombstone is denied; permitted operation recovery can still return a recorded result. Only the title can be edited. To change contents, load/Add, edit resulting drafts, save a new period snapshot and tombstone the old one.
