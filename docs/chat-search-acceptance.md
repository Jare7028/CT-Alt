# Desktop conversation message search

This original, read-only Chat slice adds search within a currently joined conversation. It preserves the existing Auth-user membership model and all applied Chat migrations, policies, grants and functions. Root owns hosted review/application, combined build, real Auth/browser checks and release.

## Supported API and privacy

`GET /api/chat/search` requires `tenantId`, `conversationId` and `query`. Query is trimmed,1–100 characters and matches message body case-insensitively as a literal substring. Percent, underscore, quotes, HTML-like text and SQL-shaped strings are ordinary search text. Optional `limit` is1–100 (default50); `cursor` is opaque.

`ChatSearchData` contains tenantId, conversationId, actorId, normalized query, exact total matches, messages and nextCursor. Each message contains conversation_id, sequence as decimal text, stored sender_id/name, body and created_at. Mutation client IDs and arbitrary private payloads are absent. Results are newest first by conversation sequence; timestamp ties do not affect ordering. Sequences never pass through JavaScript Number, so adjacent values above2^53 remain distinct. Timestamp microseconds are preserved. Existing normal Chat history has a separate safe-number sequence contract; this additive search DTO does not modify it.

A stable SECURITY INVOKER RPC computes exact count and bounded page in one signed RLS snapshot. The cursor binds tenant, current Auth actor, conversation, exact normalized query and sequence. Current confirmed, nonanonymous Auth user, active company, active tenant membership, actual joined conversation and any management-group role requirement are checked on every RPC. After validating its snapshot, the API performs a fresh signed RLS SELECT of the scoped conversation ID before releasing any messages, catching revocation committed during a long search. Missing access returns403; a failed final access read returns503. Authorization can change after this final check and before delivery; that unavoidable boundary does not allow continuing reads, and UI polling/scope invalidation must clear previously visible data. Owners/admins have no search override for unjoined/private conversations. Suspension, member removal and management-role demotion deny subsequent searches. A changed Auth actor cannot reuse an earlier actor's cursor. An agent-record relink alone is not a Chat identity change: existing Chat participation is keyed to tenant membership Auth user IDs, and this slice introduces no new agent policy.

The endpoint uses private/no-store headers.401 indicates absent verified sign-in;403 indicates current company/conversation denial;400 indicates invalid filters/cursor;503 indicates failed or invalid reads. Valid no-match reads alone return zero. The UI clears results on first-page failures and all access denials, invalidates/aborts requests across user, company, conversation or query changes, and reports an older-page failure while retaining the already-delivered prior page for retry. The API releases no new page when its final access read fails; previously delivered data remains subject to current-conversation polling and denial invalidation.

Search calls only the new read RPC. It never calls the existing read action, sends a message or updates Chat state. Existing table RLS and write grants remain unchanged. Search mode also pauses normal history/read-marking behavior; returning to normal Chat resumes its existing flows.
