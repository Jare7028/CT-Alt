# Shift Templates delivery contract

This independently implemented desktop increment follows [Connecteam's official Schedule Templates guide](https://help.connecteam.com/en/articles/3524929-schedule-templates), updated 17 August 2026, and [Creating Shifts](https://help.connecteam.com/en/articles/8986051-creating-shifts), updated 16 July 2026. Original CT Alt code and branding are used. Current logged-in Connecteam appearance and free-account entitlements have not been verified; public guide images include historical material. No competitor screenshots are committed.

## Delivered boundary

A company owner/admin or manager explicitly delegated to a schedule can list/search/page single-shift templates, create/edit/duplicate/delete a recipe and apply it to one date and currently assigned active worker. An application creates exactly one private draft. The current top-right Publish action publishes the displayed draft selection, respecting the period and filters. The separately retained legacy API still supports whole-schedule publication. No notifications, messages, Auth accounts or invitations are generated by templates.

Templates belong to one schedule and contain a name, title, current schedule job, start/end local minute and end-day offset. They do not retain a worker. Job color comes from the existing job; independent shift color is future scope. Recipes follow the schedule's current supported IANA timezone at apply; they do not store UTC offsets or alter prior shifts after timezone changes. First-slice precision is minutes. Existing shift capture must explicitly review minute normalization if source times contain seconds/fractions rather than silently rounding.

At most 500 retained templates per schedule, including deleted tombstones; list pages are 1–100, default 30. Search is literal, case-insensitive text. Exact count and rows share a database statement snapshot; cursors bind tenant, actor, schedule, schedule revision and filter. Every new template mutation advances schedule revision, preserving stale-write guards for legacy editors. Delete retains history and never removes existing applied drafts or published shifts. Archived schedules remain readable to managers but cannot create/edit/duplicate/delete/apply.

## API

See `lib/rota-template-types.ts` for exact public shapes. GET `/api/rota-templates?tenantId=<uuid>&scheduleId=<uuid>&q=<literal>&limit=<1..100>&cursor=<opaque>` returns `RotaTemplateData`, including `schedule` and `page.nextCursor`. POST `{tenantId,operationId,change}` returns `{saved:RotaTemplateSaved}`. Changes are strict create/edit/duplicate/delete/apply unions; all have `schedule_id`/`schedule_revision`; target operations additionally have `template_id`/`template_revision`. Apply chooses `agent_id`, `date`, `start_occurrence`/`end_occurrence` (`''`, `earlier`, `later`) and `allow_overlap`.

Recovery POST `{mode:'reconcile',tenantId,operationId,action,scheduleId,templateId}` returns `RotaTemplateReconciliation` directly. `templateId` is null only for create; duplication identifies its source. Recorded recovery returns the original bounded acknowledgement. Not-recorded recovery atomically closes the operation UUID so a delayed original write cannot commit later. A failed recovery read is not proof of absence.

Server body parsing uses streamed 8KiB byte limits, fatal UTF8, duplicate-key rejection and strict typed schemas; responses use private/no-store. SQL independently checks fields/types/scope and owns authorization, idempotence and time conversion. API Auth and current database access are rechecked before returning validated output.

## Database and preservation

Only the new additive migration creates `rota_shift_templates`, `rota_template_audit`, private operations and template RPCs. All applied migration bytes, legacy `save_rota`/`read_rotas`, other module function identity/grants/RLS and data remain unchanged. The public RPCs are authenticated-only empty-search-path invokers; bounded private definers perform writes under explicit actor checks. Public tables have manager-only signed SELECT RLS with browser writes revoked; private operation rows have no signed table grants or policies.

Write/recovery lock the original actor's operation UUID, then the existing tenant row mutex, actor Auth/membership, schedule and any delegated grant. Current confirmed active access is rechecked after locks. UUID receipts bind exact canonical payload, actor, action and original target schedule/template. A replay returns its original result without another audit, revision or shift. Changing payload/scope or replaying a closed operation conflicts. Current loss of permission blocks receipt recovery. Recovery after archival remains available to a permitted manager without replaying the change.

Apply uses an active roster worker; linked Auth membership must remain active. Directory-only workers follow existing scheduler behavior and need no new accounts. Server/database resolves target wall times by offset enumeration and exact timezone round-trip: missing times are rejected; repeated times require earlier/later choice; malformed/skipped dates and unsupported timezone names fail closed. Duration must exceed zero and be no more than 24 elapsed hours. End-day offset 0/1/2 preserves overnight and spring shifts spanning two midnights.

Existing archived/draft/published commitments in all company schedules count for overlaps. Adjacency is permitted. A detected overlap requires explicit acknowledgement. Apply cannot grow the company past the existing scheduler's 5,000-shift read capacity. The old independent scheduler path remains unchanged and retains its separately documented whole-payload limit.

## Verification and future scope

New configuration tests check strict UTF16/text/date/query schemas, body bounds/UTF8/duplicate keys, scoped cursor and exact initial-page checks, signed Auth/current-access rechecks, receipt/action/target/revision validation, recovery proof and actionable errors. The owned local PostgreSQL/Storage runner applies current baseline once, inserts synthetic retained rota data, snapshots every prior public/private application table/function/ACL/RLS/policy and compares all data after the additive migration. SQL tests cover CRUD, revisions, permission/tenant boundary, publication privacy, literal pagination, UUID replay/absent closure, archival, DST/folds/gaps/half-hour offsets/skipped dates, suspended workers, capacity and exactly-one applied draft. Genuine concurrent sessions cover commit/rollback recovery, competing revisions, grant revocation and old/new scheduler serialization.

Local database tests are not genuine Auth/browser acceptance or hosted release. Those and independent review/check/build/CI/production verification are integrator-owned release gates. No hosted schema is authorized to be treated as applied merely because this candidate exists.

Still missing: Day/Week save/load/preview/rename/delete and add-versus-replace confirmation; empty-week flow; drag/drop; assignment-preserving templates; independent shift color; Jobs/Layers/List grouping; recurring daily/weekly/monthly series and 100-occurrence rules; open/unassigned/group shifts, qualifications/capacity and claims/approvals; scheduler-specific Requests/history/pending states; notifications, all-day/location/notes/tasks/import and main scheduler pagination. CT Alt's general-work Requests kanban does not implement scheduler claim approval.
