## Authorization and independent identity

Only the current confirmed, nonanonymous, active company owner may activate, create or change visibility. Other roles have no implicit management entitlement. Delegated Directory management remains a separate gap requiring an explicit feature grant and a referenced grant UI.

Confirmed active members may read only visible external Work Contacts once Directory is active. The owner management view may include hidden contacts as an explicit CT Alt policy choice. Nonowner reads must not expose hidden contacts, IDs, totals, revisions, search matches, cursors or audit/receipt data. Inactive Directory catalog reads are owner-only for activation; nonowners are denied. Do not widen Agents RLS or read Auth emails. Work Contacts are new independent UUIDs with no app-access, workforce, recipient, clock or schedule identity.

Reads and writes freshly check Auth, company and membership. A held privileged response must not restore protected content after a later 401/403. Permission denial precedes stale-revision errors. Every direct table policy and authenticated RPC must enforce these boundaries; hiding UI is not authorization. New mutation/reconciliation functions lock operation, company, Auth and membership in the existing consistent order, then new Directory state/contact rows. No old function, relation, policy or trigger may be replaced. Avoid FKs from new tables to legacy parent tables; existence and authorization remain freshly checked under locks.

## Data and protocol

New company state tracks activation, management revision and a separate visible revision. Hidden-only mutations must not change the nonowner-visible revision. New contacts store tenant UUID, independent UUID, name, optional description/phone/email, visibility, revision and timestamps. New bounded owner audit and private actor-bound operation receipts support durable recovery. The state is lazily created by an authorized mutation or closed-absence reconciliation; reads never write. First activation is a real atomic operation. No accounts, invitations, notifications, messages, calls or emails are created by saving.

Internal limits: 1,000 retained contacts and 20,000 retained private operations per company, including recorded and closed-absence operations. Page at most 100 rows, coherent complete list/search up to the retained bound; cursors bind tenant, actor, current role/scope, search and that scope's revision. Full list totals cover exactly the current authorized scope. No hidden counts or unkeyed fingerprints appear in public DTOs. Existing recorded receipts remain recoverable at capacity; a new absence closure at full capacity fails without falsely declaring no write.

Input limits in raw UTF-16 units: name 1–100 after trimming, description at most 1,000, phone at most 64, email at most 254, search at most 100. Reject invalid Unicode and C0/C1 controls. Bound raw inputs before trimming; empty optional channels are permitted. Phone/email are plain bounded optional strings; do not impose undocumented E.164, mandatory-channel or vendor email rules. Only name is an internal record identity requirement; do not invent a visible required marker or instructions. Store plain text, never markup or arbitrary URLs. New input normalization never rewrites old Agents or historical data.

The strict `/api/directory` interface uses private/no-store responses, duplicate-key rejection, fatal UTF-8 and at most 64 KiB JSON. GET accepts tenantId, optional q/limit/cursor; `mode=access` is a bounded fresh permission/activation read. POST mutation shape is `{tenantId, operationId, change}`. Change is a strict union: `{action:'activate', directory_revision}`, `{action:'create', directory_revision, name, description, phone, email}` (initially visible), or `{action:'visibility', directory_revision, contact_id, contact_revision, visible_in_app}`. No caller actor, role, custom URL or profile fields.

Reconciliation is `{mode:'reconcile', tenantId, operationId, action, contactId}`; contactId is null for activation/create and a UUID for visibility. Original recorded ACK is independent of current contact revision/existence. Same operation with changed payload conflicts; closed absence permanently prevents later delivery of that operation. No automatic mutation resend after lost acknowledgement. Lock and recheck current owner authority before any reconciliation or mutation.

DTOs have schemaVersion 1, company, actorId, role, canManage (owner only), active and current scope viewRevision. Catalog adds search, contacts and page `{total,nextCursor}`. Contact fields are id/name/description/phone/email/visible_in_app/revision/created_at/updated_at; nonowners only receive visible rows. A mutation ACK binds tenantId/actorId/operationId/action, directory revision, optional contact ID/revision and activation result. The core author freezes exact types before UI integration; root reviews all privacy and coherence checks.

No unsupported detail links or selection controls. Search and automatic paging must examine the full authorized list, not only the first 100 contacts. Generation, unmount, company, Auth and role fences reject late responses. New errors preserve an unresolved write gate until recorded or durable closed-absence recovery.
