## Boundaries and schema

New additive Forms migration only; all17 prior baselines stay byte-identical. Forms was recorded as20261004063200 and applied once; all18 recorded identities and SQL bytes are immutable. Tenant-bound forms, fields/schema snapshot, fixed Auth-user assignments, actor response rows, immutable response-history and private operation receipts. Use current confirmed nonanonymous Auth identities and active tenant/membership. Original Auth user ID determines respondent ownership; agent-record relinks never transfer answers. Owner/admin management does not imply respondent assignment. Managers/employees see only current assigned published forms and their own responses.

Drafts allow0–500 eligible selected Auth-user IDs; publication requires1–500 plus at least one answerable field. Bound schema to50 ordered unique UUID fields, descriptions to5000 UTF16, field labels100, form name100/description500, text answer5000, choices50 distinct stable option UUIDs with nonblank labels100. Schema JSON≤128KiB, answers JSON≤64KiB, semantic/raw mutation request≤262144 UTF8 bytes. Reject NUL/unpaired surrogates, unknown/duplicate properties, invalid enums/IDs/revisions and oversized payloads at API and SQL boundaries. Retain valid Unicode and meaningful original content. Numeric draft text may be incomplete while typing; submitted numeric values use a documented finite decimal grammar, at most12 integer digits and6 fractional digits, with strict server/Postgres numeric validation. No exponent/nonfinite values. Yes/no uses boolean, single choice an option UUID, multiple choice unique option UUIDs. Description fields have no answers; reject forged hidden/unknown fields.

Schemas become immutable after first publication in this delivery, including archive/restore. Stable field/option labels and original submitted snapshots are retained. Published metadata, current fixed assignment and respondent-edit setting may change through revisioned management actions. Archive hides respondent access, retains submitted management read/history and makes answer edits/review/progress/submission read-only; restore returns its previous draft/published state without silently changing schema or audience. No physical deletion. Current unassigned/inactive actors cannot access form content or past answers through this module; owner/admin retains scoped management history. These are explicit CT Alt retention/access decisions where the reference guides are incomplete.

Each form/response has positive integer revision (1..2147483647); expected0 is allowed only for an absent response. Reject overflow before any write. Names of authors/respondents retained as bounded snapshots. Response snapshots retain original form schema/title, first submittedAt/original Auth author and last content-edit author/time (lastEditedAt), distinct from updatedAt for review/status changes. Review status never makes an old answer editor appear to have acted at the review timestamp. Progress autosaves overwrite only the original actor’s partial row and create no answer history. Every post-submission answer content edit appends prior immutable answers/history, references the original frozen schema without duplicating it, and increments revision; first submittedAt does not reset. Editing answers clears reviewed status; marking reviewed is an explicit owner/admin action, never a side effect of reading. No automatic notifications. Enforce50 submitted content edits per response and4,096 retained answer-history rows across the deployment with an inaccessible monotonically increasing counter. Acquire its mutex/row after actor/operation63 and company64 but before form/response rows. No deletion, credit or pruning; this is a retained-history bound, not a statement of physical database free space. Limit failure occurs before answer/audit/receipt changes.

## Authorization, concurrency and recovery

Public tables signed SELECT-only RLS; anonymous/direct signed writes denied. Public RPCs authenticated-only SECURITY INVOKER with empty search_path; narrowly scoped private SECURITY DEFINER helpers and receipt/history internals default-deny. No privileged app credential. Every write checks current role/access both before and after normative lock waits, and before an old receipt acknowledgment or returning data. Reuse actor+operation advisory seed63 then company seed64, then the deployment history allocation mutex/row when applicable, followed by form then response rows; do not introduce reverse locks. Audience/schema validation and write must share this serialized current state. UUID operations are actor/tenant/payload bound; same request retries acknowledge once, different payload is denied, and no receipt restores revoked access.

Separate save-progress, submit-response, edit-response and explicit review actions. Progress saves accept partial bounded answers; submit/edit validate required answerable fields and every actual typed answer against the immutable schema. One response per tenant/form/original actor; only original actor may autosave/submit their response. Admin editing is a distinct management operation with administrator attribution and audit. Save/submit must fence exact current form/response revisions. An assignment/form edit or concurrent response change returns conflict without discarding local content; any current403 clears private UI and locks recovery.

Field-free operation reconciliation contains only action+UUID under existing actor/company session key, waits the same operation mutex using a fresh VOLATILE snapshot, then rechecks current role/resource authority. Definitive absence records a private actor/company/action/UUID tombstone under that mutex, so an original HTTP write arriving after recovery cannot commit; it permits a new explicitly initiated UUID only. Repeated reconciliation preserves that absence and action binding. Never infer absence from unlocked STABLE reads. Recorded operation receipts retain a canonical payload hash and minimal acknowledgment, without copying partial answers into an immutable autosave history. Browser recovery does not persist answers, schema, titles, names or filters. Uncertain writes lock independent reads/actions until signed recovery; requests/controllers/epochs and actual React handlers enforce this even if disabled DOM controls are bypassed. Navigation/actor/company/view/schema changes invalidate pending reads and decoded acknowledgments, clear private data and abort requests. Old responses cannot restore form/submission/edit capabilities after departure or revocation.

Autosave is debounced, serialized, bounded and original-actor scoped. While one save is in flight, retain subsequent in-memory edits for the next save against the acknowledged response revision; do not launch overlapping writes or reuse an operation UUID for new content. Submit flushes pending save and fences actual latest form/response revisions. Unknown acknowledgment locks and preserves a field-free marker, not an automatic retry of answer bytes. An explicit Save progress action may accompany autosave but is not a substitute for the documented interruption behavior. Only a durable acknowledgment can display Saved. Pending debounce or unload/navigation does not prove a save; retain accurate Unsaved/Saving/Saved status and never claim the field-free marker can recover discarded unsent answer bytes. Do not rely on unload/sendBeacon delivery. Do not claim cross-device autosave until fresh server reload is tested.
