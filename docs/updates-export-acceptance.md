# Desktop Updates recipient CSV export

This additive CT Alt increment exports the entire selected recipient-status scope of one Update, independent of the displayed 50-row analytics page. It is original functionality, not a claim that the CSV format exactly matches Connecteam. The reviewed additive SQL is applied; consumer release remains pending. No hosted queries/mutations, real workforce data, account interactions or paid resources were used by this worker.

## Supported behavior and API

Owner/admin Engagement → Export CSV downloads every assigned recipient matching all/viewed/unviewed/confirmed/unconfirmed for the current Update. Fixed audiences are bounded at 500. The selected status is an explicit CT Alt design choice; exported fields/format are also explicitly ours. Archived Updates and historical suspended recipients remain accessible under current management authority. Auth-user recipient identity and stored display name are retained independently of agent-record links. A nonrecipient admin can export management analytics; this does not grant personal engagement.

`GET /api/updates/[id]/recipients/export` accepts only `tenantId` and optional `status` (all default), plus the dynamic UUID. Duplicate, unknown, cursor, limit and malformed parameters are rejected. All rows matching the status are exported; no client-side pagination iteration or silent truncation is used. An empty selected status is a legitimate header-only CSV.

The six columns are `User name`, `User ID`, `Viewed`, `Viewed at (UTC)`, `Confirmed`, `Confirmed at (UTC)`. Values use Yes/No; confirmation disabled uses **Not required** and an empty confirmed timestamp. As in existing analytics, unconfirmed filtering means null confirmation timestamp even when confirmation is not required. View/confirmation values are first recorded timestamps, not a count of repeat views. SQL preserves original microseconds while converting the instant to UTC, formatted `YYYY-MM-DDTHH:mm:ss.ffffffZ`; JavaScript never rounds it through a Date or Number.

UTF8 CSV includes a BOM, CRLF row endings, all cells quoted and quote doubling. Existing `csvCell` neutralizes spreadsheet formula/control prefixes. No email/mobile phone, comment body, private note or arbitrary profile data is exported. A 1MiB byte bound safely covers 500 names with 100 nonBMP codepoints and both precise timestamps; oversized or >500 datasets are refused as a whole with 413.

Success: `text/csv; charset=utf-8`, `private, no-store`, attachment filename `updates-<UUID>-recipients.csv`. Fencing headers are `X-CT-Alt-Actor-ID`, `X-CT-Alt-Company-ID`, `X-CT-Alt-Update-ID`, `X-CT-Alt-Recipient-Status` and `X-CT-Alt-Role`, taken only from signed validated data. UI must verify them against current scope, abort/fence held reads on identity/post/filter/tab changes, and check again after decoding the Blob before downloading. It must preserve existing mutation recovery locks. No row data is stored for export recovery.

Errors are private/no-store JSON: sign-in401, invalid scope400, current access403, lifecycle/content change409, supported-size413, read/validation503. Internal diagnostics are redacted. Errors never create an empty successful file or claim a download completed.

## Database authorization and snapshot

One new `public.read_update_recipients_export(target_tenant uuid,target_post uuid,status_filter text default 'all')` is STABLE SECURITY INVOKER with empty search path. It uses existing current confirmed/nonanonymous active company/membership/Auth authorization and existing signed SELECT-only RLS. It captures post identity/status/revision/content revision, requireConfirmation, exact unfiltered counts, exact filtered count and the complete sorted UUID recipient rows in one statement snapshot. It deliberately does not join recipient eligibility, so retained suspended-recipient records survive. It refuses total audiences above500 before aggregating export rows.

The additive CLI-generated migration, now recorded as `20261004004405_updates_engagement_export.sql`, creates only that function. PUBLIC/anon/authenticated/service_role default EXECUTE grants are explicitly revoked before intended authenticated EXECUTE; no baseline definition/owner/ACL/table/policy/grant is changed. There is no new definer, table, write or service-role key.

The API calls existing signed `read_updates_access` after the snapshot, verifying actor, exact current owner/admin role, company/post access and snapshot post status/lifecycle/content revisions. Revocation denies download; lifecycle/content change asks for refresh rather than releasing stale metadata. Counts and recipient timestamps remain a coherent initial snapshot even if another recipient subsequently views/confirms. There are no view marks, audit rows or receipts from reading/exporting. Authorization cannot be guaranteed to remain unchanged after the final successful recheck and delivery.

Strict DTO validation checks identity/scope, safe exact counts, complete matched count, prefilter/filter coherence, supported role/state/content, codepoint-safe stored names, precise UTC timestamp grammar, confirmation/view implications, no private arbitrary fields, unique ascending recipient IDs and null/status semantics.
